# 代码评审

只读评审：产出发现与依据，不顺手改代码。结论必须可追溯到具体文件、行与规范出处。

## 评审顺序

1. 读根 [AGENTS.md](../../../AGENTS.md) 的不变量与安全边界，再读改动涉及的 Note（`implemented/architecture/`）。
2. 看 diff：`git diff --stat` 先判断改动面，再逐文件精读，不要只看摘要。
3. 按下面的检查清单核对，逐条给出「通过 / 有疑问 / 违规」。
4. 输出按严重度分组，每条写：`文件:行`、现象、依据（不变量或 Note 章节）、建议动作。

## 检查清单

**契约与边界**

- 是否新增了字面量 API 路径？HTTP 路径必须来自 `src/types.ts` 的 `API_ENDPOINTS`。
- 客户端是否值导入了非平台的 `@deepseek-ai/*` 模块？跨插件协作必须走 cordis 服务。
- 是否绕过 `src/types.ts` 另建了跨半契约（重复类型、并行枚举）？
- 持久化是否只写 `$DSH_HOME/storages/`？是否有启动期强制建目录或读盘（应为惰性）？

**运行时正确性**

- `ctx.on(...)` 拦截器：事件名与载荷是否与宿主一致？是否在禁用路径上提前返回而漏掉副作用？
- `ctx.effect` 的资源是否都返回了清理函数（定时器、MutationObserver、rAF、React root、HTTP 路由、MCP 客户端）？
- 会话级设置与全局默认的回退链（`global` / `workspace` / `custom` / `inherit`）是否在读写两侧一致？
- 错误处理：`catch` 是否吞掉了本应上抛的失败？是否会把坏数据静默写成默认值而不可追溯？

**客户端 DOM 操作**

- 是否为「插槽能覆盖的能力」？能用 `slots.register` 就必须用插槽。
- 选择器是否依赖宿主类名（`navCell`、`heroWorkspaceRow` 等）？依赖处是否容忍元素缺失（不得抛错）？
- 观察者回调是否做了去抖/合并，避免每次 DOM 变更都全量扫描？

**文档与记录**

- 非平凡改动是否新增/更新了 Agent Note，且 `implemented/` 中的描述与代码一致？
- `README.md` 与 `README.zh.md` 是否同步？
- 是否新增了"一处事实两处写"的重复？

## 输出要求

- 先给结论（可合入 / 需修改 / 需讨论），再列问题。
- 问题按 `严重 / 中等 / 轻微` 分组；每条必须带可验证依据，不接受"感觉不太对"。
- 没有发现问题时，明确说明检查了哪些面、哪些面无法在静态评审中确认（例如 GUI 行为），不要给出泛泛的肯定。
