# 对齐 DSH 新版本

目标：宿主换版本后，让每一处宿主调用都停在当前版本最直接的写法上。升级不是改版本号，是重新审一遍"我们还在用旧做法吗"。

## 步骤

1. **定两端。** 起点 = `package.json` 的 `engines.dsh` / peer 区间（我们声明的支持下限，也是唯一验证过的版本）；目标 = `$DSH_INSTALL_DIR/package.json` 的 `version`。
2. **读官方文档。** 按 [定位升级文档](references/locate-upgrade-guide.md) 找目录——**`v<T>` 是离开版本，不是目标版本**。只读命中 [宿主包与占用面](references/host-packages.md) 的条目。
3. **核对占用面。** 逐项确认每个服务、成员、事件仍在且语义未变。
4. **找新增通道。** 文档只讲破坏不讲新增。插件还能跑、但官方显然给了更直接做法时，按 [宿主包与占用面](references/host-packages.md) 末节 diff 两侧类型声明。
5. **改代码。** 采用新通道，**同时删除旧实现**，不保留两条路。
6. **抬门槛。** `engines.dsh` 与 `peerDependencies` 同写新下限；`dsh-client-ui-primitives` 跟 shell 的实际 seed 走。
7. **同步文档。** `README` 双语兼容行、`.agents/architecture/` 受影响段落、新增 Note。
8. **校验。** 按 `pre-push-checks` 取最小命令集合。

## 不留兼容实现

只保留当前版本的最简实现，不写任何前向兼容分支。三类判定：

**违规——探测宿主 API 是否存在。** `typeof ctx.get('x').y === 'function'`、`x.y?.()`、为旧宿主留两套并行路径。宿主版本由 `engines.dsh` 裁定，不匹配就该拒绝加载，而不是降级运行。

**违规——官方有更直接的通道，仍包装或模拟其行为。** 旧写法即使还能跑也要换掉并删除。判据是"官方是不是为这件事专门加了 API"：若有，自维护那套就是债务。

**允许——捕获运行时输入错误并降级。** 目录不存在、宿主拒绝某个路径、外部配置非法，这些是运行期事实而非版本差异。把失败落进可见的"未生效"列表是正确处理。

判断不了时问：**这段代码在"宿主永远是最新版本"的假设下还需要存在吗？** 答案是否，就删。

## 验收

- 每个宿主调用都能指出它来自当前版本的哪个 API。
- `grep` 不到对宿主服务成员的存在性探测。
- 兼容区间与实际验证过的版本一致，且 `engines.dsh` 与 peer 同步。
- 每个取舍都写进了 Note，包括**否决了哪些新通道**及理由。
