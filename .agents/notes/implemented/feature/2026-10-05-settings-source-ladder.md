# Agent Note: 面板的配置来源阶梯

Status: implemented

## Problem

会话设置页的四个面板（子代理模型、MCP 服务器、技能、沙箱目录）都在同一组三维作用域（会话 / 工作区 / 全局）上写入配置，因此每个面板都要回答同一个问题：**当前显示的这一层配置，是用户在这一层设的，还是从上级继承来的？**

沙箱面板最初没有回答这个问题：它任何时候都可编辑，靠"首次编辑自动切到自定义"隐式覆盖，来源 tab 缺失。后果是用户看不出目录列表来自哪一层，也无法在不编辑的前提下查看上级到底授予了什么。

## Proposal

### 一、统一的来源阶梯

四个面板共用一条判定，实现在各自 section 内（见"重复"一节）：

```
scope === 'global'    → 'custom'（编辑的就是全局层，永远可编辑）
scope === 'workspace' → mode === 'custom' ? 'custom' : 'global'
scope === 'session'   → mode === 'custom' ? 'custom' : (mode ?? defaultMode)
                        defaultMode = 有工作区 ? 'workspace' : 'global'
```

`isReadonly` 随之定义为"会话或工作区作用域下来源非自定义"；`global` 恒可编辑，因为没有更下一层可跟随。

### 二、只读态必须显示上级的规则，而不是空列表

这是本面板与"只读即灰掉"的普通做法分开的地方。来源非自定义时，本层通常**没有**自己的 `allow`（那是继承的本质），若照直渲染本层字段，界面会显示"未配置"——而实际上上级可能正授予三个目录。

因此只读态调用 `resolveEffectiveSandbox(sessionConfig, workspaceConfig, globalConfig)`（客户端镜像，与 `resolveEffectiveMcp` 同构）渲染**实际生效**的规则，并在标题处标注只读；空列表文案也分叉为 `emptyInherited`，避免与"确实没配"混淆。

### 三、切换来源以当前生效规则为起点

点「自定义」时，初始 `allow` 取自当前生效的规则，而不是空数组：切换动作读起来是"接手我本来就在拿的东西"，而不是看起来像清空了配置。离开自定义只写 `mode`，本层 `allow` 不参与解析（服务端 `resolveEffectiveSandbox` 已如此），因此切来源不会污染任何层的数据。

### 四、会话的实际生效模式由服务端给出

面板需要知道当前沙箱模式才能提示"额外目录仅在 `workspace-write` 下生效"。`sandbox/mode` 是宿主会话投影，浏览器读不到，所以服务端在 `SandboxCapabilityInfo.effectiveMode` 里附带，经 `ctx.sandboxPolicy.overrideOf(session) ?? defaultMode` 解析；无会话（新建会话页）时用部署默认值，那正是该会话将启动的模式。取不到该服务时字段缺省，提示自动隐形，不回退成猜测值。

## Alternatives considered

- **只读态留空 / 灰掉**：实现最省，但把"继承到三条授权"显示成"什么都没配"，是主动误导。
- **客户端自行读 `sandbox/mode` 投影**：浏览器侧没有该投影的读取通道（官方 UI 走 `useProjection`，本插件的页面 props 不保证携带），且新建会话页根本没有会话可读。
- **抽公共组件承载阶梯**：正确的长期形态，但会同时改动三个已工作的面板，超出本次范围，记为后续合并候选。
- **只读态额外弹一条通知**（沙箱面板曾如此）：已删除。其余三个面板只靠控件禁用与 tab 高亮表达只读，沙箱不该是例外；且该通知内部重复（徽标说"只读查看"，紧接的句子又重说一遍）。若日后确需这句"如何切换"的指引，落点应是**四个面板一起**加，而不是让沙箱重新成为特例。空列表仍由 `emptyInherited` 说明来源，那是唯一会真被误读的情形。

## Acceptance criteria

- 会话作用域下出现 `配置来源：` 与三个 tab；选中项高亮。
- 选择"跟随全局默认"时输入框与增删控件不可用，列表显示**全局层**的目录；点「会话自定义」后转为可编辑，且列表内容从继承的规则延续。
- 无工作区时「工作区默认」tab 不出现；工作区作用域下 tab 为「全局默认 / 工作区自定义」；全局作用域无 tab。
- 阶梯的七种组合解析结果与 `resolveEffectiveMcp` 一致（已实测：会话自定义 / 会话→全局 / 会话→工作区(自定义) / 会话→工作区(跟随全局) / 无会话+工作区自定义 / 无会话+工作区跟随 / 全空）。
- `effectiveMode` 在挂载了 `ctx.sandboxPolicy` 时解析出正确模式，未挂载时缺省而不报错（已实测）。
- `pnpm run verify` 全绿。

## Risks

- **重复**：阶梯与只读判定在四个 section 间是复制而非共享，上游改动其一不会传播到其余三处。这是本次有意接受的代价（抽取会触及三个已工作的面板），属于后续合并的候选，不是终态。
- **只读态引入对 `resolveEffectiveSandbox` 的客户端依赖**：该函数已存在且与服务端解析同构，但两处若漂移，界面显示的"生效规则"会与实际执行的不一致。
- **`effectiveMode` 依赖 `ctx.sandboxPolicy`**：该服务不在时提示消失（安全方向），但用户也就看不到"当前模式下不生效"的警告。
- **只读态无显式指引**：用户需自行发现来源 tab 可点。四面板一致优先于此；若实际反馈确有困难，按上文的落点统一补，不单独给沙箱加。
