# Agent Note: 宿主升级流程与"不留兼容实现"纪律

Status: implemented

## Problem

宿主升级这件事此前没有任何载体。`0.2.2-rc.3` 那次对齐暴露了三个反复出现的失败模式：

**升级文档读错对象。** `docs/upgrade-guide/v<T>/` 描述的是**离开 vT、前往下一版**，不是"到达 vT"。按目标版本名去找目录会读到不存在的路径，空跑一次才反应过来。

**文档只讲破坏，不讲新增。** rc.1 的 19 条升级条目对本插件**一条都不适用**，真正该改的三件事（软链授权硬失败、`registerWritableRoot` 新通道、`connectionStatusOf` 权威化）全部来自两侧类型声明的比对，不读 `.d.ts` 就发现不了。

**旧写法只要还能跑就不会被删。** 插件此前包装 `ctx.sandboxPolicy.resolve()` 并自建 prime 缓存；宿主后来专门加了 `registerWritableRoot()`，包装层变成纯债务，却因为没有报错而一直留着。同类问题还有 MCP 连接态：用工具计数与挂载时间戳推断，而宿主早已提供真实状态。

这三件事都不是"版本号变化"，但每个都在等着下一个人重犯。

## Decision

新增 `upgrade-dsh` 技能承载升级流程，并把"不留兼容实现"写成可判定的三层规则。

**技能结构。** `SKILL.md`（790 units）放八步流程与三层判定；查阅型内容拆进 `references/host-packages.md`（宿主包与占用面清单）与 `references/locate-upgrade-guide.md`（文档定位与 `v<T>` 陷阱）。只有 `SKILL.md` 受 800 单元预算约束，`references/` 不受，所以这份清单不必挤进每轮上下文。

**起点由声明决定。** 起点取 `package.json` 的 `engines.dsh` / peer 区间，目标取 `$DSH_INSTALL_DIR/package.json` 的 `version`。官方 `references/upgrading.md` 说"manifest 区间只界定候选、不能当起点"，那是给不了解自身历史的通用插件写的；本仓库的纪律是声明即事实，区间写着 `>=0.2.2-rc.3` 就意味着"只在 rc.3 上验证过"。

**三层判定写进技能与 `code-review`。** 违规：探测宿主 API 是否存在（`typeof x.y === 'function'`、`x.y?.()`、两套并行路径）。违规：官方有更直接的通道仍包装或模拟其行为。允许：捕获运行时输入错误并降级（目录不存在、宿主拒绝某路径）——那是运行期事实，不是版本差异。核心判据一句话：**这段代码在"宿主永远是最新版本"的假设下还需要存在吗？**

**判定不设自动闸门。** 考虑过新增 `verify-no-compat` 脚本，否决了：固定脚本只能查"探测了不存在的成员"，查不出"旧 API 仍可用但官方有更好的了"——而后者正是本次三处改动里最贵的两处。这类判断只能是阅读时的判断，故落在 `code-review` 的检查清单里。

**`code-review` 腾位置而非扩预算。** 该文件原为 798/800，新增"宿主 API 对齐"组需要约 50 单元。改写 `## 评审顺序` 与 `## 输出要求` 两段冗余（3 步并 2 步、去掉重复措辞）腾出空间，最终 778/800——**低于改动前**，同时多了新章节。放宽 `SKILL_BUDGET` 是 `pre-push-checks` 明文禁止的做法。

## Alternatives considered

- **新增 `verify-no-compat` 闸门**：否决。只覆盖"探测不存在的成员"这一种形态，而"有更好的 API 却用旧的"无法静态判定；一个只覆盖三分之一的闸门会让剩下三分之二显得已被检查过。
- **技能只管版本号抬升**：否决。本次真正花时间的三件事没有一件是版本号，只写版本号会漏掉全部实质工作。
- **依赖官方 `dsh-doc` 技能承载文档定位**：否决为该技能的**基础**。它只存在于 Agent 预设里、不保证已安装，且它的 `upgrading.md` 没写 `v<T>` 那个陷阱。仍保留一句交叉指引。
- **单文件技能**：否决。宿主包清单约 15 项，塞进 800 单元会挤掉流程本身；`references/` 不受预算约束，且 `verify-md-links` 会校验链接不腐。
- **把 `pre-push-checks` 的 package/lock 相关行搬进新技能**：否决。三个技能各自回答一个独立问题，且都已贴近预算，任何收编都会挤掉已有内容。

## Consequences

- **升级有了固定入口**：说"宿主更新了"就触发该技能，不必每次重新推导流程。
- **`references/` 链接是新的出错面**：`verify-md-links` 会校验它们，改名要同步。
- **`code-review` 仍距上限 22 单元**：下一次想加检查项时，必须先精简而非直接追加。
- **"删除旧实现"依赖评审纪律**：没有闸门兜底，只有 `code-review` 的清单项与技能里的判据。若将来发现旧实现长期滞留，再考虑半自动的 `grep` 检查。
- **宿主包清单会腐**：它声明的是"本插件消费哪些宿主面"，新增宿主调用时要同步更新，否则升级时会漏检。
