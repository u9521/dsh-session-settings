# Agent Note: 沙箱行编辑的焦点丢失与误删

Status: implemented

## Problem

「额外可写目录」的每一行一旦开始输入就不可用：描述框里打一个字符，光标掉到页面 body；打出的空格当场消失。删除按钮单击即删。

根因是一条回路，不是两个 bug。行内输入 → `updateRow` → `commit` → `onChange` 把整份 `allow` 交给 controller → 父组件带着新的 `sandboxConfig.allow` 回到面板 → 面板的 `signature`（`JSON.stringify(displayEntries)`）变化 → effect 里 `setRows(toDrafts(...))` 用 `nextKey()` 给**每一行**重新发 key → 所有 `input` 卸载重建。焦点随旧节点一起消失，而 `fromDrafts` 的 `trim()` 又把刚打进末尾的空格规范化掉，于是句子永远接不上词。

删除走同一个 `commit`，同样重发 key——但删除的问题不是焦点，是它没有第二道确认。

## Decision

**编辑期由本地草稿拥有行，props 只是种子。** 面板记住两个签名：`lastSignature`（上次据此渲染的 `displayEntries`）与 `lastPushedSignature`（本面板上次提交出去的样子，由 `commit` 与 `switchSource` 记录）。只有当签名变化且**不是**自己刚推出去的那份时，才重新播种。来源切换、scope 切换、重新加载、重置照旧重播；自己的回声一律不采纳。

行 key 因此在行的整个生命周期内稳定：`toDrafts` 只在播种新建行时调 `nextKey()`，编辑不再重建任何一行，React 按 key 复用同一个 DOM 节点，焦点与未 trim 的输入都留在原处。

**删除改成两步。** 第一次点击把按钮变成「确认删除」并加危险色描边，3 秒内第二次点击才真的删除；按钮失焦、切到别的行、或在任何行上编辑都会撤销这一步。行以 key 而非下标标识，避免一次提交后撤销到错误的行。同一个两步交互复用到模板弹窗里的模板删除。

这里删除的只是草稿，真正落库还要点「保存」，所以这道确认防的是误点，不是不可逆损失——文案也就只说「确认删除」，不写"不可恢复"。

## Alternatives considered

- **给 `SandboxAllowEntry` 加稳定 id**：UI 行状态会渗进策略契约，服务端 normalize 与 interceptor 的 `- "<path>" — <desc>` 渲染都要跟着认一个与授权无关的字段。
- **改成失焦才上抛**：输入期父层看不到最新规则，保存按钮与 scope 判断都滞后一拍，违背"每条 grant 都要显式保存"的立场。
- **用 `React.memo` + 稳定回调缓解**：只掩盖重建，不解决 props 回声覆盖本地草稿，"空格被吃掉"照旧发生。
- **删除用 `window.confirm()`**：MCP 服务器删除用它，但那是模态打断；行级草稿删除的代价小得多，且原生弹窗无法用 `t()` 本地化。
- **删除走撤销而不是确认**：需要一条撤销入口与生命周期，比两步点击贵。

## Acceptance criteria

- 在路径框或描述框连续输入整句（含空格）时不丢焦点、不丢空格。
- 删除需两次点击；3 秒后自动撤销，点别处或编辑任一行也撤销。
- 来源切换、scope 切换、重新加载、重置后行列表按新的显示来源重播。
- 模板填充与手工新增仍会追加行，且新行可立即编辑。

## Consequences

- **回声识别依赖 JSON 序列化形状**：`commit` 用 `JSON.stringify(fromDrafts(next))` 记录，而父层写回的也是同一份规范化结果，两者必须逐字一致。若将来 `fromDrafts` 或服务端再规范化一次（例如排序），回声会认不出而被采纳，症状会回到"编辑时重播"。缓解是两边共用同一个 `fromDrafts` 语义，且此约束写在此处。
- **外部刷新不重播**：若将来有主动轮询覆盖 `sandboxConfig` 的路径，其结果与本面板当前草稿完全相同时会被当作回声忽略。当前没有这样的路径。
- **3 秒可能偏短**：手慢的用户会看到按钮弹回「删除」并需要重新点第一次。比误删便宜。
